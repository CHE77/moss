# CommonGround: один цикл в Moss + hREA

Сценарий: кооперативу нужны 10 буханок; пекарня берёт обязательство, расходует 5 кг муки и 3 часа труда, производит и передаёт 10 буханок. В Moss участники договариваются и координируют работу. В hREA проверяются экономические записи и остатки. Unyt — отдельный, необязательный эксперимент с расчётом в тестовой валюте.

Это стенд для проверки пригодности платформы. Между инструментами Moss, hREA и Unyt здесь ещё нет автоматической интеграции. Записать ссылку на задачу недостаточно, чтобы выполнить экономическую операцию.

**Проект рабочего процесса:** [алгоритм, ресурсы, производственный граф, соглашения и выбор финансового ядра](PROCESS_AND_ARCHITECTURE.md). Документ описывает семь действий пользователя, предлагаемые автоматические переходы и решение «использовать / доработать / создать новый модуль». Реализация этих переходов ещё не выполнена.

Дополнительный кандидат: [оценка Requests and Offers](REQUESTS_AND_OFFERS_ASSESSMENT.md), включая различие релиза/dev, существующие автоматические связи с hREA и недостающие функции. Выпуск скачан и проверен, установка в Moss пока NOT RUN.

Кандидат производственного контура: [оценка Carbon Farm Network](CARBON_FARM_NETWORK_ASSESSMENT.md) и [живой цикл CFN на двух peers](CFN_CYCLE_RESULTS.md). Ресурсы, рецепты, события и синхронизация работают в проверенных пределах. Полный цикл — FAIL: UI расход не связан с партией, а отдельный API transfer оставляет 8/0 вместо 5/3. Для повторного чтения сохранённых тестовых записей: `node labs/commonground/cfn-verify.mjs`. Проверщик не выполняет экономические операции; exit 1 отражает найденные ошибки.

Для знакомства с приложением: [CFN для фермера](CFN_FARMER_GUIDE.md) — русские термины, действия фермера и мастерской, пошаговый пример и схема ожидаемого потока. Для следующего интерфейса: [предложение редактора ValueFlows](VALUEFLOWS_EDITOR_PROPOSAL.md) — Svelte Flow, разные блоки ресурсов/процессов, состояния потребности/обязательства/факта и связь с командами CommonGround.

## Посмотреть hREA

Из корня этого форка, с установленным Git, Node.js и Nix:

```bash
node labs/commonground/run.mjs inspect
node labs/commonground/run.mjs prepare-hrea
node labs/commonground/run.mjs build-hrea
node labs/commonground/run.mjs ui-hrea
```

Открыть <http://localhost:8888>. Runner создаст каталог `../hrea-commonground-lab`, рядом с Moss. Сборка выполняет upstream `nix develop`, `yarn install`, `yarn build`; первый запуск потребует загрузки инструментов и сборки Rust/WASM.

`ui-hrea` вызывает upstream `yarn dev`: он пересоздаёт sandbox именно этого отдельного checkout. Поэтому для просмотра использован специальный каталог, не существующий рабочий проект hREA. Этот запуск поднимает один conductor. Перед запуском освободить порт 8888, если на нём работает пример applet из `yarn dev` Moss; сами окна Moss можно оставить открытыми.

Нужные сущности в UI/API: Organization/Person, Unit, ResourceSpecification, Intent, Plan, Process, Commitment, EconomicEvent, EconomicResource. Проверить, какие из них доступны для создания именно через UI; пробел в интерфейсе записать отдельно от отсутствия операции в API.

Для воспроизводимой демонстрации API:

```bash
node labs/commonground/run.mjs demo-hrea
node labs/commonground/run.mjs test-hrea
node labs/commonground/run.mjs repro-hrea
```

`demo-hrea` запускает демонстрацию самих разработчиков hREA. `test-hrea` — наш хлебный цикл. Оба используют изолированный временный harness: их данные удаляются после теста и не появляются в отдельно запущенном UI. В нашем API-тесте один Holochain-подписант и три экономических актора; это не тест трёх P2P-узлов.

`repro-hrea` — минимальная отдельная проверка передачи: выпуск 10 штук у отправителя, начальный нулевой запас получателя, один `transfer`, чтение обоих остатков без cache. Она не добавляет компенсирующих событий. В живой проверке опубликованного hApp передача оставила 10/0 вместо 0/10; см. [вывод и ограничения](RESULTS.md).

Runner не делает `reset` или `checkout` в существующем каталоге, проверяет точный commit hREA и не перезаписывает отличающийся файл теста. Для обновления собственного изменённого теста сначала сравнить его с `labs/commonground/hrea-cycle.ts`.

Если окружение уже подготовлено отдельно, команды сборки, UI, demo и test принимают `--current-env`:

```bash
holochain --version
hc --version
lair-keystore --version
kitsune2-bootstrap-srv --version
rustc --version
node --version
yarn --version
node labs/commonground/run.mjs build-hrea --current-env
node labs/commonground/run.mjs demo-hrea --current-env
node labs/commonground/run.mjs test-hrea --current-env
node labs/commonground/run.mjs repro-hrea --current-env
node labs/commonground/run.mjs ui-hrea --current-env
```

В этом режиме runner использует программы из `PATH`, проверяя Holochain и hc 0.7.x до запуска. Закреплённый checkout и защита изменённого теста сохраняются. Это позволяет использовать официальные бинарники того же выпуска, если полный `nix develop` требует сборки conductor из исходников. Источник бинарников, SHA256 и версии остальных программ нужно записать в RESULTS; проверка версии сама по себе не проверяет происхождение бинарника. Режим по умолчанию остаётся `nix develop`. Установка зависимостей использует `--frozen-lockfile`.

Для проверенного Holochain 0.7.0 нужен Lair 0.7.1; Lair 0.6.3 из Moss вызывает отказ conductor. В отдельном окружении использованы `kitsune2-bootstrap-srv` 0.5.0 и Rust 1.95.0 с `wasm32-unknown-unknown`. Conductor и keystore Moss оставляются прежними.

## Участники и инструменты Moss

Быстрый вариант: создать отдельную тестовую группу в уже работающем Moss и пригласить два дополнительных тестовых профиля. Для трёх независимых окон из исходников есть конфигурация `weave.dev.config.commonground.ts`:

```bash
yarn check:binaries
yarn electron-vite dev -- --dev-config weave.dev.config.commonground.ts --agent-idx 1
```

После создания группы агентом 1, в двух других терминалах из этого же checkout:

```bash
yarn electron-vite dev -- --dev-config weave.dev.config.commonground.ts --agent-idx 2 --sync-time 20000
yarn electron-vite dev -- --dev-config weave.dev.config.commonground.ts --agent-idx 3 --sync-time 20000
```

Роли: 1 — кооператив; 2 — пекарня; 3 — координатор. В dev-режиме Moss создаёт временные профили; повторный запуск не проверяет восстановление прежней идентичности или данных. Сохранение после перезапуска проверять отдельно в обычных тестовых профилях. Публичный `networkSeed` в конфигурации предназначен только для тестовых данных.

В CommonGround Lab установлены 17 совместимых выпусков из каталогов Moss 0.15, включая KanDo, Converge, Who's In?, Acorn, Unyt и Carbon Farm Network App. Версии, источники и SHA256 записаны в [evidence/tools.json](evidence/tools.json); проверенные действия и ограничения — в [RESULTS.md](RESULTS.md). Установка остальных инструментов подтверждает доступность пакета; их функции требуют отдельных проверок. Для повторения активировать установленные инструменты в каждом новом профиле группы.

| Инструмент | Действие в цикле | Что проверить |
| --- | --- | --- |
| Группа Moss + Vines | создать общий чат и обсуждение заказа | все три участника видят группу, участников и сообщения |
| Acorn | создать потребность «10 буханок» и связать её с целями сообщества | изменение цели видно другим; есть пригодная ссылка на объект |
| Who's In? | собрать участников выпечки/выдачи | участие, отказ и актуальный список видны другим |
| Converge | согласовать количество, срок, распределение | решение и его статус доступны всем участникам |
| KanDo | задачи «купить/выделить муку», «испечь», «выдать» | назначение, статус и ссылка на потребность/решение |
| hREA, отдельно | записать обязательство, входы, выход и передачу | реальные изменения остатков и связи экономических записей |
| Unyt, отдельно | перевести 30 тестовых единиц от кооператива пекарне | отправка, принятие, окончательное состояние на обеих сторонах |

В каждом объекте использовать маркер `commonground-bread-v1`. Где инструмент поддерживает WAL, вставить ссылку на объект соседнего инструмента. Где такой поддержки нет — записать URL/идентификатор вручную и отметить ограничение. Экономические идентификаторы hREA сохранять отдельно; соответствие между участником Moss и экономическим актором пока задаётся вручную.

## Экономический цикл и критерий успеха

Фиксированные параметры находятся в `cycle.json`; API-проверка — в `hrea-cycle.ts`.

| Шаг | Запись hREA | Ожидаемый результат |
| --- | --- | --- |
| Начальный остаток | `raise`, мука 25 кг | у пекарни 25 кг муки |
| Потребность и план | Intent → Commitment; Plan → Process | заказ и обязательство на 10 буханок |
| Расход | `consume`, 5 кг, `inputOf` процесса | осталось 20 кг муки |
| Работа | `work`, `effortQuantity` 3 часа, `inputOf` | записаны именно 3 часа, не денежная оценка |
| Выпуск | `produce`, 10 штук, `outputOf` | у пекарни 10 буханок |
| Передача | `transfer`, источник и получатель, `fulfills` и `satisfies` | у пекарни 0, у кооператива 10; событие связано с обязательством |
| Расчёт, по желанию | операция Unyt на 30 тестовых единиц | отдельная подтверждённая операция, привязанная к этому циклу |

API-тест читает данные обратно без Apollo cache, проверяет оба вида остатков (`accountingQuantity` и `onhandQuantity`), единицу труда и обратные связи процесса/обязательства. Он завершается ненулевым кодом при несовпадении.

Закреплённый код hREA имеет обработчик `DecrementIncrement`, который сохраняет количество исходного ресурса прежним. Живой цикл и минимальный `repro-hrea` подтвердили неизменившиеся остатки 10/0 после `transfer` на опубликованном и собранном hApp. Вывод сохранён в [RESULTS.md](RESULTS.md); компенсирующие `raise`/`lower` не применялись. Исходник для разбора: <https://github.com/h-REA/hREA/blob/79c8d4fb98c4f7f9a8cf3f7dd69690d6d1334d85/dnas/hrea/zomes/coordinator/hrea/src/rea_economic_event.rs>.

Наличие записи `transfer` или ссылки `fulfills` само по себе не доказывает корректный учёт. Для успеха должны одновременно сходиться остатки, единицы измерения и связи.

## Проверить P2P и Unyt

Экономический учёт не требует обязательной денежной оплаты: ресурсный цикл должен работать и без Unyt. Для сравнения финансовых вариантов провести отдельный тест:

| Проверка | Действие | Критерий |
| --- | --- | --- |
| Прямой расчёт | одна операция на 30 тестовых единиц | обе стороны подтверждают сумму и окончательный статус |
| Кредитное правило | попробовать операцию в пределах и сверх заданного лимита | правило ограничивает операцию, а не только предупреждает в UI |
| Отложенное принятие | отключить получателя, отправить, вернуть его в сеть | промежуточный статус явный; завершение и баланс сходятся |
| Повтор операции | проверить повтор запроса с тем же внешним ID, если API это поддерживает | одна экономическая операция; если такого API нет — `BLOCKED` |
| Маршрут доверия | A доверяет B, B доверяет C; попытаться заплатить A → C | реальный маршрут и ограничения каждого ребра; bridge валют не считать эквивалентом |
| Параллельные расходы | два запроса расходуют один доступный лимит | суммарный разрешённый расход не превышает лимит |
| Резервный подписант | только если поддержана смена полномочий между устройствами/узлами | прежний подписант теряет право; старые запросы не принимаются повторно |
| Наш интерфейс | изучить доступный API, конфигурацию правил, условия лицензии ядра | возможно подключить CommonGround, в том числе будущий мобильный клиент |

До проверки не считать подтверждёнными маршрутизацию кредитов по графу доверия, распределённое резервирование лимитов и передачу права подписи. Не копировать приватный ключ между узлами как замену протоколу резервного подписанта.

Unyt документирует P2P-валюты, кредитные лимиты, Smart Agreements и асинхронное принятие платежей. При этом открытый sandbox не доказывает открытость и пригодность всего ядра: ссылка на submodule `unytco/unyt-app` при проверке недоступна (404), sandbox имеет Apache-2.0, библиотека Smart Agreements — GPL-3.0. Зафиксировать, какие компоненты доступны для сборки и изменения, прежде чем выбирать основу финансов. Документация: <https://unyt.co/docs/>; sandbox: <https://github.com/unytco/unyt-sandbox>; agreements: <https://github.com/unytco/smart_agreement_library>.

В реальной интеграции сохранять пару «ID события hREA ↔ ID операции Unyt» и обрабатывать состояния расчёта и повтор запросов. Сбой после платежа и до записи hREA не должен запускать новый платёж. Такая связь здесь ещё не реализована.

Для Moss проверить доставку сообщений и обновлений после временного отключения одного участника от сети без закрытия его dev-окна. Для hREA проверка синхронизации между разными подписантами — отдельный следующий стенд; текущий API-harness её не покрывает.

## Отчёт и решение о платформе

Для каждой строки записать `PASS`, `FAIL`, `BLOCKED` или `NOT RUN`, версию, шаги, фактический результат, ожидаемый результат и свидетельство (лог/скриншот/ID). Не ставить `PASS` по наличию кнопки или модели данных.

- **Moss как оболочка:** время прохождения цикла, пригодность инструментов, количество ручных переносов, доступность совместимых выпусков и ссылок.
- **hREA как экономическое ядро:** точность остатков и связей в API; отдельно — удобство интерфейса и многопользовательская работа.
- **Unyt как расчётный модуль:** пройденные финансовые проверки, доступность исходников/API и возможность задать наши правила.

Результаты живой проверки, ошибки и непройденные требования фиксируются в [RESULTS.md](RESULTS.md). Решение о переходе CommonGround принимать после результатов, особенно передачи ресурсов и требований P2P-финансов.

Проверки без Nix, зависимостей Moss и запущенного conductor:

```bash
node --test labs/commonground/run.test.mjs
node --check labs/commonground/run.mjs
node labs/commonground/check-syntax.mjs
```

Проверка `.ts` через Node 24 сначала удаляет типы штатным `stripTypeScriptTypes`, затем проверяет синтаксис ES-модуля без исполнения и загрузки зависимостей. Прямой `node --check file.ts` в проверенном Node 24.21.0 не удаляет типы. Проверка синтаксиса не заменяет `yarn typecheck` Moss или сборку и реальные вызовы API hREA. Официальные инструкции hREA: <https://github.com/h-REA/hREA/blob/happ-0.5.0-beta.1/docs/getting-started.md>.
