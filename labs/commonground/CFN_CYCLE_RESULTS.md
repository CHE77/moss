# CFN: проверка производственного цикла на двух узлах

**12 октября 2026, Europe/Amsterdam. Полный цикл — FAIL.** Проверен установленный CFN 0.6.0 в Moss desktop 0.15.8 / Holochain 0.6.1. Это выполнение на двух независимых conductor, а не только чтение исходников.

CFN сохраняет ресурсы, рецепты, запрос, процессы и связи событий с обязательствами. После отключения второго участника записи синхронизировались. Однако проверенный интерфейс расходует ресурсы без ссылки на партию, а передача не меняет остатки даже в отдельном API-тесте с явными ID. Поэтому считать этот релиз готовым экономическим ядром CommonGround нельзя.

## Сценарий и границы

В CommonGround Lab созданы синтетические акторы **CG CFN Farm 2026-10-12** и **CG CFN Workshop 2026-10-12**. Каждый создан через CFN своего Moss-профиля. Авторы подписанных записей различаются и совпадают с ключами соответствующих peers. Установленные DNA hrea, hrea_facets_0 и migration одинаковы у обоих участников.

Тестовая метка: `commonground-cfn-2026-10-12`. Ранее существующие агент, единица kilogram и служебные facet groups сохранены. Денежные операции не выполнялись. CommonGround и код Moss/CFN не изменялись; tools не форкались.

План опыта: начальная партия 25 кг сырья у Farm → расход 5 кг / выпуск 5 кг подготовленного волокна → расход 5 кг / выпуск 4 кг пряжи → передача 4 кг Workshop. Производство выполняет Farm; два участника здесь не означают распределённое производство на разных предприятиях. Для проверки backend создана отдельная партия с меткой `-probe`; её записи не исправляют результаты основного сценария.

## Отдельный API-тест партии и передачи

Этот тест отделяет проблему выбора партии в UI от поведения backend. Использован API **установленного CFN**, его embedded hrea DNA; отдельный hREA 0.7 из предыдущего хлебного опыта здесь не участвует.

1. Первый peer создал отдельную партию 10 кг Raw fiber у Farm.
2. `consume 2 kg` с явным `resourceInventoriedAs` изменил оба количества **10→8** — PASS.
3. Второй peer создал свою отдельную нулевую партию Raw fiber у Workshop.
4. Первый peer записал `transfer 3 kg` с provider Farm, receiver Workshop, **resourceInventoriedAs исходной партии и toResourceInventoriedAs конечной партии**.
5. Ожидание: 5 кг у Farm / 3 кг у Workshop. Факт: **8 / 0** — FAIL для обоих количеств.

Событие transfer сохранено с обеими ссылками. Его ID: `uhCkkixgN8heAHv7xXSJCWwvjYgSp51rWi3DkxUgpDcQZYe1QBEBk`. Оба peers и прямое чтение подписанных resource entries подтверждают 8/0. Причина внутри backend не локализована. Проверка не добавляла компенсирующих raise/lower или ручного редактирования количества.

У обновляемой probe-партии менялись возвращаемые action IDs/revisions, а сохранённое поле `id` было null. В доказательства включены returned revisions; стабильность идентификаторов ресурса при обновлениях требует отдельного разбора. В transfer подставлены ID, возвращённые текущим чтением соответствующих партий.

## Синхронизация и восстановление

Второй процесс Moss остановлен в **10:15:36 UTC**, восстановлен в **10:16:28 UTC** с прежним `agent2` profile. Между ними первый peer записал `spin-consume` и `spin-produce`. После открытия CommonGround Lab → CFN второй peer прочитал оба события. Сохранён тот же ключ участника.

В конце одинаковы **10 экономических событий, 5 ресурсов, 1 диагностический план** и ссылки исполнения. Это включает 6 событий основного сценария (начальный raise, четыре производственных факта, UI transfer) и 4 события API probe. Проверено попарное локальное соединение через loopback bootstrap; работа через интернет, разделение сети и одновременная запись конкурирующих резервов не проверялись.

Счётчик presence Moss на финальном скриншоте второго peer показывает 1/2. Его соответствие состоянию conductor отдельно не проверялось; вывод о синхронизации CFN основан на чтении одинаковых подписанных данных с двух действующих узлов, а не на этом индикаторе.

## Причины и наблюдаемые ограничения

- **Loading recipes — пустой каталог.** Первоначальный запрос вернул `recipeProcesses.edges = []`. В установленном `13.033b49ff.js` placeholder выбирается при нулевой длине массива; после создания рецептов исчез. Это не подтверждение зависшего запроса.
- **Генератор зависит от предметных соглашений CFN.** В установленном `_helper.63340933.js` начальная потребность получает `stage: {name: "Ship"}`. В `13.033b49ff.js` выбор рецепта учитывает имя/ID стадии; найденный путь также ищет вход того же resource specification, что выход. Наша цепочка из разных материалов не построилась. Совместимость полного эталонного fiber-набора CFN не проверена; эти находки не означают, что никакие рецепты CFN не работают.
- **Редактор запроса падает на null.** Воспроизведена ошибка `_helper.63340933.js:9:7939` после карандаша. После ошибки потребовалось переоткрыть CFN с исходным Moss query context. Reload глубокого маршрута без `view`/`group-hash` оставил пустой экран; возврат к исходному applet view восстановил UI и сохранённые записи.
- **UI расход не выбирает партию.** В прочитанном instance/save-event пути `14.2227f93c.js` переменная списка ресурсов начинается пустой; события расхода в нашем опыте сохранены без ссылки. Отсутствие влияния на остаток подтверждено данными, независимо от полного аудита этой функции.
- **Transfer backend не прошёл.** Даже явные исходная/конечная партии не дали ожидаемых остатков. Расход с явным ID прошёл, поэтому сбои UI и передачи следует исправлять отдельно.
- **Приёмка и автоматический платёж не проверены.** Total cost `$0` и связи с обязательствами не доказывают согласие владельца, блокировку запасов, качество результата или разрешение расчёта.

В ходе подготовки проверочного harness были исправлены собственные ошибки: недостающие GraphQL скобки, селекторы повторяющихся DOM IDs и ISO-строка `created` вместо используемого CFN числового timestamp. Они не приписаны CFN. Перед повтором отклонённого createPlan подтверждено отсутствие плана на conductor. Неизвестный результат остальных записей автоматически не повторялся.

## Решение для CommonGround

**Продолжать CommonGround на 0.8; CFN оставить сравнительным стендом и источником предметных решений.** Из CFN полезно брать структуру рецептов, типы сущностей и представление входов/выходов по стадиям. Полный перенос этого релиза без исправления поведения перенесёт и подтверждённые ошибки.

Первый вертикальный срез CommonGround должен проверять единый контракт: выбранный `resourceId` + владелец + стадия + количество → разрешённый резерв/обязательство → событие исполнения → проверяемые остатки обеих сторон → приёмка → заранее разрешённый расчёт. Запись события без партии не должна выдавать успешный расход склада. Это предметные требования к новой реализации, а не реализованная здесь автоматизация.

С нуля нужны наши правила полномочий, подтверждения резервов, восстановления и финансовый адаптер; существующие UI/модели CFN можно адаптировать после проверки совместимости и лицензии. Исправление CFN/hrea, перенос на 0.8, проверка мощностей, конкурирующих резервов, чужого доступа и автоматического расчёта в этом опыте **не выполнялись**.

Предыдущее исследование исходников использовало Graph Verify проекта carbon-farm-network, generation `2026-10-11T22:57:35Z`; coverage использованных TS/Svelte paths без записанных проблем. Опубликованный minified bundle отдельно не индексирован: здесь прочитаны конкретные маршруты/адаптеры из распакованного файла с проверенным SHA256 и проверены вызовы установленного приложения. Негативные выводы ограничены описанными сценариями; полного аудита CFN нет.
